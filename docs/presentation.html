ONE PAGE

一页看懂：它是什么，改了什么

它不是一个“模型展示页”，而是一段可以被操作的自然：风有方向、种子有惯性、 蒲公英会生长也会淡出，时间可以被拨动。重构的目标，是让这段自然继续成立， 同时让它的“控制面板”变成一套可读、可测、可改的 Vue 应用。

14.9k行引擎代码（30 个模块）
19个 Vue 组件（app 层 23 文件）
0场景层 DOM 查询
12组自动化功能用例

玩法

风滚草移动 → 风场变化；点击种草 → 老树开花；三个风眼 → 风车转动； 上升气流 → 起飞；枯泉 → 种子恢复；日晷 → 拨动时间。

重构

原 main.js 同时负责场景与界面，直接修改 40+ 处 DOM。 现在拆成 engine / store / components 三层， 场景层不再触碰 DOM。

验证

无头 Chrome + 真实输入事件，覆盖启动、风、种植、解锁、相机、时间、 声音、明信片、移动端、静态出帧与响应式。

核心判断 保留“自然的手感”，把“界面的复杂度”交给框架。 Vue 3.5 · 浏览器构建
PRINCIPLES

设计目标：不画风景，画“风留下的证据”

  • 克制。没有 HUD 仪表盘式堆叠；信息只在需要时出现（上下文提示、toast、能力胶囊）。
  • 可解释。每一处动效都对应一个可读的物理量：风速、种子惯性、太阳高度、草叶弯曲。
  • 可误触抵抗。拖动镜头不种植、点击 UI 不起风、双手操作时视角与风场分离。
  • 可降级。低配设备减草量、关后期；无 WebGL 给说明；不支持录像自动改存照片。
  • 可维护。状态只走一个方向；组件不知道 three.js，引擎不知道 DOM。

一句话原则

“让画面自己说话，
让界面在需要时出现，
让代码在改动时不互相牵连。”

这三条分别对应：视觉克制、交互反馈、框架分层。

20+ 处 getElementById / querySelector；UI 的生命周期与场景循环共用一套时序。

  • 改动面大。改一个 HUD 文案，要读 1.2k 行场景代码。
  • 难测试。没有组件边界，只能整页跑；断言只能看 DOM 文本。
  • 状态分散。能力、明信片、录制、上下文提示各有一份“真相”。
  • 性能与结构耦合。每帧写样式与 UI 更新混在一起，无法独立优化。
  • 移动端重复。按钮的显示/隐藏/文案在 main.js 和 mobile-controls.js 里各写一遍。

症状

“换个提示语的文案”级改动，需要理解整个渲染循环。

目标

让界面“声明它要什么”，让场景“只负责算出来”。

底线

不改动任何一处物理/着色器行为，不牺牲手感。

约束（写进注释与评审清单）

  • 引擎不得出现 document.querySelector。
  • 组件不得写 runtime.api.objects.*.xxx =。

  • 高频数值只能走 sky paint 或 CSS 变量。

为什么不做成响应式

  • 位置/透明度/墨色每帧变，reactive 会带来无意义的依赖追踪。
  • Vue 的调度器只为“结构/状态”服务；逐帧数值交给 CSS 变量更直接。
  • 所有写入集中在一个文件、一个快照；易审查、易关停。

边界规则

高频（每帧）：paint → CSS 变量
中频（>50ms）：store 字段（风、录制秒数）
低频（事件）：模板重渲染（能力、胶片、明信片）

去重WeakMap 缓存，相同字符串不写
结构DOM 仍由 Vue 渲染
可回退删掉 painter 即可关停

功能实现：风、种子、时间、地标

逐项说明“看得见的效果”背后在算什么，以及为什么这样算。

MECHANISM 01

局部风场：风只作用在手指经过的地方

// 1 · 记录屏幕路径：每段带“当时的空气速度”
trail.push({ ax, ay, bx, by, age: 0,
             airX, airY, airZ });   // 0.45s 后消失

// 2 · 查询某点的空气
//    取附近 trail 段中影响最大的一段
air = segmentAir * 径向衰减(radiusPx)

// 3 · 屏幕速度 → 世界方向
right = camera.right; up = camera.up;
dirWorld = right * vx + up * (-vy);

// 4 · 风速 → 强度（带平滑与反向闸门）
strength += (raw - strength) * (1 - exp(-attack * dt));

radiusPx 随屏幕短边缩放并夹在 165–520 px；草另有一层更小、会滞后跟随的草地风场。

  • 不是全屏风。指针离开后余流只保留 0.45 s。
  • 风力互相叠加。手势风、风滚草风源、自然风各自独立，采样时取最强源。
  • 草更“钝”。方向低通、强度慢滤、反向时压到约 15%，避免左右抖动。
  • 种子更“灵”。在风区里响应快，离开后靠惯性继续飞。

一个可观察的因果

从蒲公英上滑过：花头抖、种子被扯下；在别处滑过：只有草和花粉动，花头完全不受影响。

输入pointermove 路径
映射屏幕 → 世界
衰减径向 + 时间
叠加取最强源
MECHANISM 02

自然风：让草地“呼吸”，但不抢走手势

三个慢周期

约 60s / 26s / 11s 的正弦叠加，形成缓慢的强弱起伏。强度始终低于蒲公英自然脱种阈值。

≈ 0.12 – 0.59 m/s

随机阵风

每隔 8–23 s 插入一次 2.8–7 s 的柔和阵风，强度与相位每次重新生成，避免可预测的循环。

direction drift: 两个慢正弦

草叶表现

草与草毯的 shader 共用 uStrength / uWind；根部固定在实例位置，只有上段按圆弧弯曲。

5 种草 × 3 种子变体 = 27 InstancedMesh

风的三个来源
手势短生命期的局部阵风
风滚草移动/升空注入世界空间风源
自然持续、缓慢、方向漂移

手感上的取舍

自然风不能强到“自己把种子吹走”，否则玩家会失去“我起了风”的因果感；它只负责让静止画面仍然活着。

// dandelion-field.js
spawnAt(point) {
  size = 0.8 + random * 0.4;
  grow   = 0.6 + random * 0.3;   // 秒
  life   = 50 + random * 20;     // 秒
  // 超过上限时移除最老的一株
}

// 落点限制：r ≤ 118m，高度 ≤ 30m，坡度 ≤ 0.44
if (r > 118 || point.y > 30) return;
if (world.slopeAt(x, z) > 0.44) return;
  • 不是瞬间出现。生长有 0.6–0.9s 的过渡，避免“贴图弹出”。
  • 只有花头种子会张开。茎、叶、花托保持稳定，种子按各自节奏脱离。
  • 空花头会补满。整头从空到满约 20s，飞行中的种子可比茎多停留一会儿。
  • 上限是体验的一部分。1 → 3 → 6 → 15 随能力增长，防止画面被塞满。

种植判定

短按（<650ms、位移<8px、非多指）才种植；拖动镜头、点击 UI、双手缩放都不会误种。

MECHANISM 04

种子的惯性：风改变它，而不是“摆到”目标位置

// dandelion.js · 每帧只做一件事：
// 向“自己所在位置”的局部空气速度靠拢
exposure = localSpeed / maxSpeed;
response = 0.34 + 1.55 * exposure;

vel += (localAir - vel) *
       (1 - exp(-response * dt));

// 在风区：response 快，迅速被带走
// 离开风区：response = 0.34/s，缓慢衰减
// 还有轻微重力、空气摆动、飘落姿态

脱离瞬间继承一部分当地风速，并获得一个沿径向的小踢腿。

  • 个体差异。每颗离体种子锁定约 ±10% 的尺寸，并在 0.45s 内平滑过渡。
  • 层次感。同一阵风里的种子不再像同一张剪贴画复制。
  • 主茎会摆动。花托、绒球与仍在花头上的种子共用根部支点；已飞出的种子不受影响。
  • 影子贴地。茎摆动时影子不跟着离开地面。

体验结果

快速划过后，种子会继续飘、慢慢减速；下一次手指经过附近，还能再次改变它们的轨迹。这让“风”有持续感，而不是一次性动画。

反馈分层：不打断，但绝不让你猜

① 首屏提示

屏幕底部的操作提示随能力增长逐条追加；首次交互后 1.6s 停留 + 1.2s 淡出，不遮挡画面。

WASD · 拖动 · 滚轮 · 点击

② 上下文提示

靠近地标时出现“在附近种下一株蒲公英”“E · 唤醒种子合唱”“三个风眼 · 2/3”；取景时变为“P · 拍照”。

只在变化时写入 store

③ 一次性反馈

Toast 负责解锁、明信片、录制完成、错误提示；2.8s 自动消失，可被下一条覆盖。

role="status" aria-live="polite"

  • 能力胶囊：地面 / N 株 / 相机 / 多株 / 起飞 / 恢复 / 时间，已解锁高亮。
  • 风力计：右下角细条，随手势 / 移动 / 自然风变化。
  • REC：顶部红点 + 秒数，录制中持续更新。
  • 声音：风底噪随速度与高度变化；种植、快门、解锁、起降各有提示音；可一键静音。
  • 明信片条：五张 chip，点亮即归档，重复拍摄不会重复点亮。
  • 片尾联系表：集齐五张自动出现，可继续漫游。
原则 永久信息（能力 / 明信片 / 风力）常驻；过程信息（提示 / toast）短暂；错误信息给下一步动作。

UX 05

性能：把预算花在“看得见的地方”

27草的 InstancedMesh（5 种 × 3 变体）
2独立渲染层（场景 / 萤火虫）
1/30物理步长上限（与帧率解耦）

  • 实例化 + LOD：草/花按距离分层，远处进入雾霭；远景草与花不参与近景密度。
  • 程序化资产：所有贴图（花瓣、绒毛、星野、地面）由代码绘制，无外部请求。
  • 萤火虫独立层：夜色遮罩之上的透明画布，不会被夜色压暗。
  • 自适应画质：?quality=coarse / 触屏自动 5000 簇、300 只萤火虫。

  • 天空旁路：每帧只写一组 CSS 变量，Vue 不参与逐帧更新。

VERIFICATION

验证：真实浏览器、真实输入、真实 DOM

  • 零依赖。没有 Node/npm：Python 启动静态服务器，直接通过 CDP 驱动本机 Chrome。
  • 真实输入。用 Input.dispatchMouseEvent / dispatchTouchEvent / dispatchKeyEvent 模拟手与键盘，而不是直接调函数。
  • 真实断言。既看 Vue 渲染出的 DOM（胶囊、toast、缩略图），也看引擎状态（株数、胶片数、时间）。
  • 真实异常。收集 Runtime.exceptionThrown、console.error 与网络错误，任何一条都判失败。
  • 软件 WebGL。SwiftShader 下帧率很低，因此用 wait_frames() 等待渲染循环，而不是 sleep 猜时间。
  • 一次一浏览器。每个用例独立启动 Chrome，避免上下文累积导致崩溃。

TRADE-OFFS

收益、代价与下一步

收益

  • 界面改动只改组件与 store，不碰场景。
  • 场景层零 DOM，可被测试与复用。
  • 触屏与桌面的显示逻辑合并为一处。
  • 高频路径仍然只有一次样式写入。

代价

  • 引入 Vue 运行时（157KB 生产包）与模板编译器。
  • 没有构建流程，模板写在 JS 字符串里，IDE 支持弱于 SFC。
  • 天空 paint 是一条需要维护的“旁路契约”。
  • 测试依赖本机 Chrome + 软件 WebGL，速度慢。

下一步

  • 可选引入 Vite + SFC，模板可近乎原样迁移。
  • 增加 prefers-reduced-motion 与画质手动档。

  • 扩展更多“风的地标”，把能力树变成可探索的地图。
